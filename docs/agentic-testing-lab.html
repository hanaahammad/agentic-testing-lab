An AI agent that does the whole QA cycle, from user story to closed bug

The testing team asked whether Claude could connect to their tools and automate the full cycle, with the agent doing the testing. This lab is a working answer: two banking apps with hidden bugs, and a QA agent that finds them, files them, and confirms the fixes.

43 tests written by the agent 11 / 11 seeded bugs found 0 false alarms on the fixed builds 1 test script repaired by the agent itself
The starting question

"Can the agent access Jira or GitHub, and can it actually do the tests?"

The key design choice

The agent writes the tests and the CI pipeline runs them. Running scripted tests is deterministic, repeatable and free. The agent's intelligence goes before the run (understanding the story, designing cases) and after it (reading failures, deciding what they mean).

Where the agent drives the app itself

In exploratory mode the agent opens a real browser and calls the API one action at a time, deciding what to try next from what it sees. That is how it hunts for new bugs. It is not used for regression, because it never behaves exactly the same way twice.

GitHub instead of Jira, for now

User stories are Markdown files in the repository, bugs are GitHub Issues, and the pipeline is GitHub Actions. The tracker sits behind one small module, so the same agent can file into Jira through its REST API or a Jira connector.

How it works

The cycle, one story at a time

Each user story goes through the same eight stages. The two amber stages are human checkpoints; the dashed one is where CI takes over.

Stage 07 in detail

A red test does not always mean the app is broken

Triage is where most of the value is. For every failure the agent decides which of three things happened, and each verdict leads to a different action.

Product bug

The app answered, but what it returned or showed contradicts the story.

→ opens one GitHub Issue, never a duplicate
Test bug

The script itself is wrong, for example it clicks a button id that is not on the screen.

→ the agent repairs its script and reruns
Environment

The app or the browser was not available. Neither the app nor the test is at fault.

→ reported, no bug filed, no repair

Applications under test

Two banks, eleven hidden bugs

NileBank

A realistic online-banking web app: sign-in with lockout, accounts overview, own and beneficiary transfers with a daily limit, beneficiaries with IBAN validation, paginated history, sign-out. Real screens, REST API and database. 7 stories, 8 bugs.

MiniBank

A tiny core-banking REST API used as the first, simplest target: open accounts, deposit, withdraw, transfer. 3 stories, 3 bugs.

What we learned building it

Lessons for a real rollout

L1

Stable test ids on screens matter more than the agent. Every button and field in NileBank has a data-testid. With them, UI tests survive layout changes, and the agent can map a screen reliably.

L2

Environment problems must not become bug reports. On the office network the browser download failed behind the company proxy. The first version called that a "test bug". It is now classified as an environment problem, and the lab falls back to the Edge already installed.

L3

Exploration finds, scripts keep. Live exploration found all eight NileBank bugs, but only scripted tests in CI prove a fix stays fixed.

L4

Keep humans at two gates. Approving test cases before automation, and reviewing the agent's scripts as a pull request, keep quality high without slowing the loop.

L5

Guardrails for bank clients. Test environment only, synthetic data, least-privilege tokens, and no ad or tracking scripts in reports (the chart library adds one by default; it is switched off).
